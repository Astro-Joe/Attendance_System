    Main.ino contains firstly, the other header files which are:
    - systemGlobal.hpp
    - display.hpp
    - peripheral.hpp
    - accessControl.hpp
    - newtwork.hpp
    - fingerprint.hpp
    Most variables that were forward declared in systemGlobal.hpp are
    properly declared here.
    It would been seen later on that this file contributes majorly towards
    the management and effective tracking of the state of the system at any
    given point in time and also the User Interface (UI) {in conjunction with
    display.hpp}.
    There are two main functions here: void setup() and void loop() and
    would be considered in some details below:
    
    ****void setup(): Contains code that run on startup, which includes:
    - Initialization of serial monitor, LCD, I2C and SPI communication
      pins, check_LED and customKeypad library.
    - Then, the connected peripherals (RTC, SD module, keypad and
      fingerprint scanner) are initialized. All files used by the system are
      created here. {see peripheral.hpp, fingerprint.hpp and network.hpp}
    
    ****void loop(): After startup the rest of the functionality of the
    system is here. I'll be discussing about some important functionalities
    here especially the use of the boolean flags...
    PS: The void loop is an all encompassing "while loop" function which cascades
    deeper into the system logic.
    
    1. Starting from the void loop - handle_background_tasks() is used for
       dynamically changing the time per minute {see systemGlobal.hpp} and
       may in future be used to handle other background tasks.
       This is followed by the system continuously running the loop waiting
       for a keypad input.
    
    2. bool refresh_screen controls the display of new screens. Each screen
       is linked to a state in enum mainPage and with an instance of
       variable mainState {see systemGlobal.hpp}. The change in the value of refresh
       screen is locked to key presses <= "3" to prevent the continuous refresh of the
       mainpage when other keys are pressed, putting strain on the microcontroller
       (I'm kinda finding it hard to justify this bit).
    
    3. Based on the value of the mainState several functions are run. I will
       be considering the scenerio where the mainstate is ATTENDANCE_PAGE as
       this is the most complex scenerio
       -- Given the case where the mainstate = ATTENDANCE_PAGE,
       attendancePage() is called {see display.hpp} and a couple of boolean flag
       values are set:
       ** refresh_screen = false: this is to set the refresh flag to the
       default state and make sure its only toggled when needed.
    
       ** waitingFlag_3 = true: for the while loop for the keypad input from
       the keypad and handle_background_tasks() {see systemGlobal.hpp}.
    
       ** keypad_enable = true: this signifies that no attendance session is
       in progress and the original attendace page menu is displayed rather
       than attendancePage_mod() {see display.hpp}.
    
       ** waitingFlag_4 = false: This monitors the attendance session timer
       and activates the automatic end of an attendance session when the
       time elapses. Value = false signifies that the timer is not currently
       running.
    
       -- Depending on the key pressed, the subState variable is changed to
       different states in the enum subPage {see systemGlobal.hpp}.
    
       -- In each subState the keypad_enable flag is used to track
       if an attendance session is ongoing or not, and different actions are
       carried out depending on that.
            -- For subState = LECTURER_SIGN_IN:
               if the flag is true, lecturer_sign_in() is called {see
               display.hpp}, if the sign in is successful its value is set
               to false, attendance mod is displayed and the timer starts
               counting. If sign in is unsuccessfully the display remains as
               previous and nothing changes.
    
            -- For subState = STUDENT_SIGN_IN:
               if the flag is false student_sign_in() is called{see
               display.hpp}, else "NO ATTENDANCE IN PROGRESS" is printed
               and the normal attendancePage() menu is displayed.
    
            -- For subState = SYS_SETTINGS_MENU:
               if the security prompt is exited: if the flag is false
               attendancePage_mod() is displayed; if the value is true,
               attendacePage() is displayed
    
    ---- I will not be going into the functionality of the system settings
    but there is a feature to keep the hotspot on only while in the system
    settings page. And depending on whether the keypad_enable flag is false or
    true the third option in the system settings menu will be "OTHER
    SETTINGS" or "END SESSION".
    
    -- Lastly, there is a while loop that runs when waitingFlag_2 is true
    and is directly in the void loop bracket. The use of this loop is to
    return to the main page when the promptInput() or Security() {see network.hpp}
    returns no value {exception for Security() when subState = SYS_SETTINGS_MENU}.

    fingerprint.hpp contains functions for the smooth functioning of the
    fingerprint scanner. The functions includes:
    - Fingerprint scanner initialization
    - Fingerprint registration
    - Fingerprint recognition
    - Resetting of fingerprint scanner
    See more below:
    
    **void fingerprint_reg(): Checks if the SD card was initialized at startup because info from the scanner is to be logged on it. It is called in student_signup() {see display.hpp} after student has been validated to be a unique entry {see network.hppfor more details}.
    There are three steps of scanning the student fingerprint, each having
    it own collor code on the scanner's ring. If any of the steps failed the
    fingerprint registration is cancelled. On successful registration the
    UID is stored in a global variable (storedUID) that is logged on the SD
    card.
    
    **void fingerprint_recog(): It is caled in student_signin(). If the fingerprint is recognized the UID linked to the fingerprint is retrieved abd stored in a global
    variable (retrievedUID) which is compared to the UIDs in the stored UID file to
    get the linked matriculation number.
    Up on failed recognition. either the student's finger was not placed
    properly or the student hadn't registered.
    
    **void reset_scanner(): This is called at startup in the situation where
    the scanner needs to be wiped clean. In this version it is manual
    enabled or disabled in the code itself but (prolly V2...) it should be
    an admin previledge. The function is advised to be used in conjunction
    with erasing_student_records() and erasinG_lecturer_records() {see
    network.hpp}, for the system to work normally.

    registered before or if a course that is about to record a has been
    registered initially.
    The logic goes as thus:
    - if the state of the device is in LECTURER_SIGN_UP and,
      -- The course is found, it signals that the course already exists.
      -- If the course was not found it signals the registration of a new
         course.
    
    - if the state of the device is in LECTURER_SIGN_IN,
      -- The course exist and matches the password: In this current version,
         it prints attendance in progress and then cheecks if the attendance
         file had already existed (see display.hpp) but it supposed to be
         the other way around. Fix coming in V2....
      -- The course exists but no password has been inputted it silently passes     that a course is being signed in.
      -- The course exists and the password entered doesn't match, it throws
         wrong password.
      -- The course doesn't exist, it signals that the course wasn't found
         in the database.
    
    - If the state is neither in LECTURER_SIGN_UP or LECTURER_SIGN_IN, we
      assume the course code and course password is coming from the
      attendance download webpage. And depending on whether the course was
      found  and password matches, the course was found and the password
      didn't match or the course was not found different actions are carried
      out.
    
    - If the target file is unable to be opened, it assumes that there is an
      error with the SD card.
    
    ****bool student_validation("some args"){see display.hpp for details on
    how its used}: This is used in  student sign-up and student sign-in to

    accessControl.hpp contains functions that have to do with gettting
    inputs from the user and also protection for pages that need
    authorization to be accessed. Two functions are used for every case
    scenerio, String promptInput("some arg") and String Security("some
    arg").
    Important things to know would be discussed below:
    
    ************Important things to know*************
    - String promptInput(String prompt) : This is used for a variety of
      scenerios like inputting password, course code, matriculation number
      and timer; with each state controlled by the funcState variable (see
      enum diffFunc in systemGlobal.hpp).
      Depending on the function state the logic changes, for example
    
      - PASSWD_FUNCTIONALITY accepts password input that must not be greater
        than or less than 8 characters (throws invalid password otherwise)
        and then returns the user input as a string which would be logged in
        the lecturer_data.jsonl.
      - COURSE_CODE_FUNCTIONALITY accepts course code input that must not be
        greater or less than 11 charaters(throws invalid course code otherwise)    ,returns the user input as a string which would be logged in
        lecturer_data.jsonl.
      - MATRIC_NUMBER_FUNCTIONALITY accepts matric number input that must
        not be greater or less than 12 characters (throws invalid matric
        number otherwise) which would be logged in the student_data.jsonl.
      - TIMER_FUNCTIONALITY converts the string input to integer, there's
        logic for constraining the time between 10mins and 120mins
      - Also depending on the state of system the "C - clear" button behaves
        differently.
    - String Security(String prompt): This used as the security wherever
      needded in the code.
      - When no code input and clear is pressed if in lecturer signin or in
        system settings behave differently.
      - The function returns a value even tho the security code is fixed
        because, depending on whether a session is ongoing or not and the
        "C" button is pressed when the code input section is empty a
        different attendance menu page is displayed (see Main.ino for more
        details on the logic)
